# AI 知识工程反馈循环

AI 知识工程反馈循环把实现和审查过程中暴露出的项目专用知识转化为持久指令，从而改善未来的智能体工作。

## 核心机制

AI 编程智能体了解通用软件模式，但不会自动知道项目已经采用的工具函数、命名规则、性能限制、回退行为、重试语义、部署约定或业务规则。这些缺口在棕地系统中最明显，因为许多关键知识隐含在代码和资深开发者的经验中。

循环如下：

1. 智能体使用当前记忆、技能和规范进行实现。
2. 人工审查发现一项智能体不知道的项目专用事实。
3. 团队把该事实分类为代码、业务或流程知识。
4. 把事实加入正确的持久控制面。
5. 未来的智能体会话继承改进后的规则集。

这就是[规范驱动开发](/wiki/concepts/spec-driven-development)背后的知识复利机制。

## 知识层级

| 层级 | 示例 | 持久归宿 |
| --- | --- | --- |
| 项目基础 | 技术栈、目录结构、数据契约。 | [Claude Code 记忆文件](/wiki/concepts/claude-code-memory-files)或项目索引。 |
| 代码级知识 | 现有工具函数、命名和模块边界。 | 记忆或任务专用技能。 |
| 业务知识 | 领域规则、回退策略、成本与重试语义。 | [Claude Code 技能](/wiki/concepts/claude-code-skills)和权威规范。 |
| 流程知识 | 审查、发布、测试和部署要求。 | 技能以及确定性的 [Claude Code Hooks](/wiki/concepts/claude-code-hooks)。 |

规则越是项目专用，通用模型正确推断它的可能性越低，记录它的价值也越高。

## 绿地与棕地路径

有两条互补的构建路径：

- **自上而下：** 从产品需求开始，编写规范和技能，再让智能体实现新系统。
- **自下而上：** 扫描现有代码库，提取隐含约定和可复用工具，由资深开发者复核，再依据实际实践构建规则库。

绿地工作偏向自上而下设计。棕地工作通常需要自下而上提取，因为真实来源分散在代码、历史和团队习惯中。

## 质量过滤器

“写清晰的代码”或“处理错误”之类通用指导价值很低。高价值内容会指明准确的项目规则：复用哪个工具、使用哪个队列或数据库、哪些错误可重试、适用哪个性能预算，以及如何回滚。

这进一步明确了[技能设计模式](/wiki/concepts/skill-design-patterns)：技能是持续演进的项目资产，而不是一次性生成的检查表；审查发现应不断修订技能。

## 失效模式

- 生成通用技能，并把形式完整误认为与项目相关。
- 把关键规则留在某个开发者的记忆或重复聊天提示中。
- 为新系统写文档，却忽略现有代码中的隐含知识。
- 把经验存进归档，却从不把反复出现的规则提升为持久规则。
- 本可由 hook 或测试确定性执行，却只写成文字说明。
